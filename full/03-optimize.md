# 03 效能優化：量測 → 假設 → 改一處 → 驗證

> 用途：系統化地找出瓶頸並優化，避免「憑感覺亂改」。
> 對應考試要點二：「運用電腦工程知識與技巧，優化特定程式與整體系統效能之能力」。
> 各領域的具體技巧見 `domain/` 內的檔案（pico-dma、pio、riscv-hazard3、multicore-sync、ros2、pico-sdk）。
> 最後更新：2026-11

---

## 0. 鐵則

1. **正確性第一。** 結果錯了，再快也是零分。每次優化後都要驗證輸出。
2. **先量測，再優化。** 沒量過就不知道瓶頸在哪。直覺常常是錯的。
3. **優化瓶頸，不是優化所有東西。** Amdahl 定律：一段只佔總時間 10% 的程式，就算快到 0，整體時間也只少 10%（約 1.11 倍）。
4. **一次改一處。** 改完立刻量測、記錄。多處一起改，無法知道哪個有效、哪個壞事。
5. **保留可回復的版本。** 每個有效的改動都 `git commit`，壞了就 `git checkout` 回去。
6. **用跟評分一樣的條件量測。** 同樣的編譯旗標（通常是 Release；pico-sdk 的 Release 預設是 `-O3`，以評分腳本為準）、同樣的輸入規模、同樣的硬體。

### Amdahl 定律速算

```
整體加速比 = 1 / ((1 - p) + p / s)
p = 被優化部分佔總時間的比例，s = 該部分的加速倍數

例：p = 0.6，s = 3  →  1 / (0.4 + 0.2) = 1.67 倍
例：p = 0.6，s = ∞  →  1 / 0.4 = 2.5 倍（上限）
```

先把 p 最大的那段找出來，才值得花時間。

## 1. 優化流程

```
① 建立 baseline：原始程式的正確輸出 + 效能數字（多跑幾次取中位數）
        ↓
② 剖析（profiling）：時間花在哪？列出各段耗時比例
        ↓
③ 分類瓶頸：運算？記憶體/匯流排？I/O 等待？同步？通訊？演算法？
        ↓
④ 列方案：每個方案估「收益 / 風險 / 實作時間」，挑最划算的
        ↓
⑤ 實作一個方案
        ↓
⑥ 驗證正確性（輸出與 baseline 相同）+ 量測效能
        ↓
⑦ 有效 → commit 並記錄；無效或變慢 → 回復並記錄原因
        ↓
回到 ②（瓶頸可能已經轉移到別處）
```

### 1.1 實驗紀錄表（一定要寫）

| # | 時間 | 改了什麼 | 正確？ | 效能（單位） | 相對 baseline | 保留？ | 備註 |
|---|---|---|---|---|---|---|---|
| 0 | 09:40 | baseline | ✓ | 1520 ms | 1.00× | — | |
| 1 | 10:05 | 熱迴圈改用 DMA | ✓ | 980 ms | 1.55× | 是 | commit a1b2c3 |
| 2 | 10:30 | 加 -O3 | ✓ | 990 ms | 1.54× | 否 | 沒差，回復 |

這張表的用處：知道哪些試過、為什麼失敗；寫狀態卡時直接複製；最後提交時知道哪個版本最好。

## 2. 量測方法

### 2.1 Linux / 容器內

```bash
time ./prog                         # real（牆鐘）/ user / sys
/usr/bin/time -v ./prog             # 若有安裝：最大記憶體、context switch 次數
for i in 1 2 3 4 5; do ./prog; done # 多跑幾次看變異
```

程式內量測（最可靠、可以只量某一段）：

```c
#include <stdio.h>
#include <time.h>
static double now_ms(void) {
    struct timespec t;
    clock_gettime(CLOCK_MONOTONIC, &t);
    return t.tv_sec * 1e3 + t.tv_nsec / 1e6;
}
double t0 = now_ms();
/* 要量的區段 */
double t1 = now_ms();
fprintf(stderr, "section: %.3f ms\n", t1 - t0);   /* 用 stderr，避免污染 stdout 的評分輸出 */
```

若環境有安裝（先用 `which` 檢查，不要自己安裝軟體）：
- `perf stat ./prog`、`perf record` + `perf report`：找熱點函式。**注意：Docker 預設 seccomp 會擋 `perf_event_open`，容器內 perf 很可能無法使用**，此時改用程式內計時或 gprof（見 `domain/c-linux-perf.md`）。
- `gprof`：編譯加 `-pg`，執行後 `gprof ./prog gmon.out`。
- `valgrind --tool=callgrind`：很慢，但很精確。

### 2.2 微控制器（RP2350 / pico-sdk）

```c
#include "pico/stdlib.h"
uint64_t t0 = time_us_64();
/* 要量的區段 */
uint64_t t1 = time_us_64();
printf("section: %llu us\n", t1 - t0);   /* printf 放在量測區段外 */
```

- 太短的區段：重複 N 次再除以 N，或用 cycle counter（見 `domain/riscv-hazard3.md`、`domain/pico-sdk.md`）。
- **printf 很慢**（尤其 USB stdio），絕對不要放在被量測的區段內。
- 用 GPIO 拉高 / 拉低標記區段，搭配邏輯分析儀（如果考場有）。

### 2.3 ROS 2

```bash
ros2 topic hz /topic        # 發布頻率
ros2 topic bw /topic        # 頻寬
ros2 topic delay /topic     # 延遲（訊息需有 header 時間戳）
```

詳見 `domain/ros2.md`。

### 2.4 量測注意事項

| 陷阱 | 說明 |
|---|---|
| 量到 debug 版 | 用跟評分相同的旗標（看 `.gitlab-ci.yml` 或評分腳本；pico-sdk 的 Release 預設 `-O3`，Debug 為 `-Og`） |
| 第一次執行較慢 | cache 冷啟動、檔案系統快取；多跑幾次取中位數 |
| 編譯器把要量的程式刪了 | 結果沒被使用時會被最佳化掉；用 `volatile` 變數接結果，或印出結果 |
| 量測本身的開銷 | 計時呼叫、printf 都有成本；量測粒度不要太細 |
| 變異很大 | 背景程式、溫度、頻率調整；看中位數與最小值 |

## 3. 瓶頸分類與對應手法

先判斷屬於哪類，再找對應手法。

### 3.1 判斷方法

| 現象 | 可能的瓶頸類型 |
|---|---|
| CPU 使用率 100%，時間跟運算量成正比 | 運算 |
| 資料量大、存取跳躍、加大資料時效能驟降 | 記憶體 / 快取 / 匯流排 |
| CPU 閒置但整體很慢，在等 I/O / 周邊 / 訊息 | I/O 等待、通訊 |
| 多執行緒比單執行緒還慢、或加執行緒沒變快 | 同步、鎖競爭、false sharing |
| 輸入稍微變大時間暴增 | 演算法複雜度 |
| 在等另一個元件（topic、FIFO、DMA 完成）| 管線不平衡、序列化執行 |

### 3.2 手法總表（由「通常最有效」排到「通常最小」）

#### A. 演算法與資料結構（收益最大）
- 降低時間複雜度：O(n²) → O(n log n) / O(n)。
- 換資料結構：線性搜尋 → hash / 陣列索引 / 二分搜尋。
- 消除重複計算：快取結果、預先計算、查表（LUT）。
- 提早結束、跳過不需要的工作。

#### B. 平行化與硬體卸載（嵌入式題目的重點）
- **DMA**：把記憶體搬移、填值、周邊資料傳輸交給 DMA，CPU 同時做別的事。見 `domain/pico-dma.md`。
- **PIO**：把精確時序的 I/O、位元打包 / 解包交給 PIO 狀態機。見 `domain/pio.md`。
- **第二顆核心**：工作切成兩半，或做成管線（core0 產生、core1 處理）。見 `domain/multicore-sync.md`。
- **重疊（overlap）**：計算與搬運同時進行，例如雙緩衝（ping-pong buffer）——DMA 填 buffer B 時 CPU 處理 buffer A。
- 多執行緒：資料切分給各執行緒，各自累計最後合併（避免共享）。

#### C. 同步開銷
- **縮短臨界區**：鎖只包住真正存取共享資料的那幾行，把計算移到鎖外。
- 減少共享：每個執行緒 / 核心有自己的資料，最後合併一次。
- 合適的鎖：短臨界區用 spinlock，長等待用 mutex / 條件變數。
- 避免 false sharing：不同執行緒寫的變數放在不同 cache line。
- 用原子操作取代鎖（單一計數器）。

#### D. 記憶體與資料存取
- 循序存取優於跳躍存取（cache / prefetch 友善）。
- 結構陣列（AoS）vs 陣列結構（SoA）：依存取模式選擇。
- 熱程式碼與熱資料放 SRAM，而非 XIP flash（RP2350：`__not_in_flash_func`）。
- 對齊資料；用適當寬度一次讀寫（32 位元一次搬，而非逐位元組）。
- 減少動態配置（malloc 在熱路徑中很慢）。

#### E. I/O 與通訊
- **批次處理**：一次處理多筆，減少每筆的固定開銷。
- 減少 printf / log；必要的輸出先寫入 buffer 再一次輸出。
- ROS 2：調整發布頻率、QoS、訊息大小；callback 內不要做阻塞操作。
- 輪詢 vs 中斷：高頻事件用輪詢或 DMA，低頻事件用中斷。

#### F. 運算層級（微優化，通常最後才做）
- 除法 / 取餘數 → 位移 / 遮罩（除數是 2 的冪次時）。
- 浮點 → 定點數（Hazard3 RISC-V 核心沒有 FPU，浮點運算全靠軟體模擬，非常慢）。
- 分支 → 無分支寫法（branchless）、查表。
- 迴圈展開（unrolling）、迴圈不變量外提。
- 使用硬體指令：`__builtin_popcount`、`__builtin_clz`、`__builtin_ctz`（Zbb 擴充可直接對應）。見 `domain/riscv-hazard3.md`。

#### G. 編譯器
- 最佳化等級：`-O2`（預設安全選擇）、`-O3`（更積極，不一定更快）、`-Os`（程式碼小，對 XIP flash 快取可能更好）。
- `static inline`、`restrict`、`const` 幫助編譯器最佳化。
- 看組合語言確認編譯器做了什麼：`objdump -d`、pico-sdk 產生的 `.dis` 檔。
- **注意**：如果評分系統用固定的建置設定，改編譯旗標可能無效或不被允許。先確認。

## 4. 方案評估

每個方案用這張表評估，挑「收益高、風險低、時間短」的先做：

| 方案 | 針對哪個瓶頸 | 預期收益 | 依據 | 風險（可能壞掉什麼）| 實作時間 | 驗證方式 |
|---|---|---|---|---|---|---|
| | | 高/中/低 + 估計倍數 | 量測 / 推測 | | 分鐘 | |

**原則**：
- 時間不多時，選「中收益、低風險、15 分鐘內完成」的，不要賭「高收益、高風險、2 小時」的。
- 有把握的小改動累積起來，常常勝過一個沒做完的大改動。
- 每完成一個有效改動就提交一次（在規則允許的情況下），確保分數落袋。

## 5. 正確性驗證

每次修改後：

```bash
./prog_original < input.txt > expected.txt   # baseline 輸出（只需做一次）
./prog < input.txt > actual.txt
diff expected.txt actual.txt && echo "SAME"  # 完全一致才算過
cmp expected.bin actual.bin                  # 二進位輸出用 cmp
```

要另外測試的邊界情況：
- 空輸入、單一元素、最大規模。
- 長度不是 2 的冪次、不是 4 的倍數（DMA / 向量化 / 展開最容易出錯的地方）。
- 對齊與不對齊的位址。
- 多執行緒：多跑幾十次，看結果是否每次都一樣（競爭條件是隨機出現的）。

## 6. 反模式（常見的浪費時間方式）

| 反模式 | 為什麼不好 |
|---|---|
| 沒量測就開始優化 | 很可能在優化不重要的部分 |
| 一次改很多處 | 不知道哪個有效；壞了不知道怪誰 |
| 優化時破壞正確性 | 零分 |
| 微優化非熱點程式 | 收益趨近於零 |
| 量 debug 版 / 量的規模和評分不同 | 結論錯誤 |
| 花兩小時在一個高風險方案 | 時間用完、什麼都沒拿到 |
| 不做紀錄 | 重複嘗試失敗的方案、忘記最佳版本是哪個 |
| 改了評分用的介面或輸出格式 | 被判錯 |

## 7. 給模型的提示範本

### 7.1 找瓶頸

```
/瓶頸
目標：{{例如：降低處理 N 筆資料的總時間}}
目前 baseline：{{數字與單位}}
量測結果（各段耗時）：
{{貼量測輸出}}
程式碼（熱點部分）：
{{貼程式碼}}

請：
1. 依量測資料判斷瓶頸類型（運算 / 記憶體 / I/O / 同步 / 通訊 / 演算法）
2. 用 Amdahl 定律估算優化各段的理論上限
3. 如果量測資料不足以判斷，告訴我還要加哪些量測點
先不要提出改法。
```

### 7.2 列方案

```
/方案
瓶頸：{{上一步的結論}}
限制：{{不能改的檔案 / 介面 / 硬體資源}}
剩餘時間：{{例如：3 小時}}

請列出優化方案，用表格：方案、針對的瓶頸、預期收益（附依據）、風險、實作時間、驗證方式。
依「收益 / 時間」排序。標出你最推薦先做的一個並說明原因。
```

### 7.3 實作

```
/實作 {{N}}
請先說明：要改哪些檔案的哪些地方、改動步驟、可能的副作用。
我同意後再給程式碼。程式碼只給修改的部分（修改前 / 修改後）。
```

### 7.4 解讀結果

```
改動 {{描述}} 之後：
- 正確性：{{diff 結果}}
- 效能：{{之前}} → {{之後}}
這個結果符合預期嗎？如果不如預期，可能的原因是什麼？下一步該怎麼做？
```

## 8. 嵌入式系統優化速查（RP2350 / pico-sdk）

| 情況 | 首選手法 | 細節 |
|---|---|---|
| CPU 用迴圈搬大量資料 | DMA | `domain/pico-dma.md` |
| 用 CPU bit-bang GPIO、等待精確時序 | PIO | `domain/pio.md` |
| 一顆核心忙、另一顆閒 | 雙核分工 / 管線 | `domain/multicore-sync.md` |
| CPU 等 DMA 完成時閒置 | 雙緩衝重疊計算與搬運 | `domain/pico-dma.md` |
| 熱迴圈從 flash 執行 | 放到 SRAM | `__not_in_flash_func`，`domain/pico-sdk.md` |
| RISC-V 核心上用 float / double | 改定點數 | Hazard3 無 FPU |
| 大量位元操作 | Zbb / Zbs 指令、builtin | `domain/riscv-hazard3.md` |
| 鎖競爭 | 縮短臨界區、分散累計 | `domain/multicore-sync.md` |
| 熱路徑中有 printf | 移除或移到最後 | USB stdio 很慢 |
| 周邊輪詢浪費 CPU | 中斷或 DMA + DREQ | |
