# 02 讀題目與文件：從零掌握系統架構

> 用途：拿到題目後的前 30–60 分鐘，用系統化的方法讀懂「題目要什麼」和「這個系統怎麼運作」。
> 對應考試要點一：「透過文件閱讀，掌握特定系統軟、硬體架構之能力」。
> 最後更新：2026-11

---

## 0. 核心原則

1. **先廣後深。** 先知道有哪些東西、彼此怎麼連，再深入任何一個細節。一開始就鑽進某個函式，很容易花一小時讀了不重要的東西。
2. **先找評分方式。** 「怎樣算對、怎樣算快、怎樣加分」決定你該讀什麼。評分沒看懂之前，任何優化都是盲目的。
3. **區分事實與推測。** 讀到的寫「事實（出處）」，猜的寫「推測」，之後用實驗確認。
4. **把理解寫下來。** 填「題目理解卡」和「架構圖」。寫不出來的地方就是還沒懂的地方。
5. **datasheet 不用全讀。** 只讀題目會用到的周邊與章節；先看該章的 Overview、圖、暫存器表、程式範例。

## 1. 階段一：盤點（5–10 分鐘）

目標：知道手上有哪些東西，不急著懂。

### 1.1 盤點指令

在專案根目錄依序執行（每個都很快）：

```bash
pwd && ls -la                       # 在哪、有什麼
find . -type f -not -path './.git/*' | head -100   # 所有檔案
find . -type f -name '*.md' -o -name '*.txt' -o -name '*.pdf' | grep -v .git   # 文件
find . -name 'CMakeLists.txt' -o -name 'Makefile' -o -name '*.cmake' -o -name 'package.xml' -o -name 'setup.py'   # 建置設定
find . -name '*.c' -o -name '*.h' -o -name '*.S' -o -name '*.s' -o -name '*.pio' -o -name '*.py' -o -name '*.cpp' | xargs wc -l | sort -n | tail -30   # 程式碼量
git log --oneline | head -20        # 有沒有提交歷史可參考
git branch -a                       # 分支
grep -rn "TODO\|FIXME\|XXX\|HINT\|NOTE" --include='*.[chS]' --include='*.py' --include='*.pio' --include='*.cpp' . | head -50   # 出題者留下的提示
ls .gitlab-ci.yml 2>/dev/null && cat .gitlab-ci.yml   # 評分流程可能定義在這
```

### 1.2 要找到的關鍵檔案

| 找什麼 | 為什麼重要 |
|---|---|
| 題目說明（README、題目 PDF） | 目標、規則、評分 |
| 評分 / 測試腳本、`.gitlab-ci.yml` | **實際上怎麼評分**，比文字描述更準 |
| 建置設定（CMakeLists.txt、Makefile） | 怎麼編譯、用什麼旗標、連了哪些函式庫 |
| 進入點（`main`、ROS node 的 `main`） | 程式從哪開始 |
| 標了 TODO / 「在此實作」的地方 | 你要動手的位置 |
| 標了「請勿修改」的地方 | 不能碰的範圍 |
| 範例輸入 / 輸出 | 正確性的基準 |

### 1.3 給模型的提示

```
/理解
以下是專案的檔案清單和題目說明。請：
1. 把檔案分類：題目說明 / 評分相關 / 建置設定 / 主要程式 / 輔助程式 / 不能改的
2. 告訴我應該依什麼順序讀，每個檔案預計花多久
3. 列出你看完後最想先確認的 3 個問題

檔案清單：
{{貼 find 的輸出}}

題目說明：
{{貼題目}}
```

## 2. 階段二：題目理解卡（10–15 分鐘）

讀完題目說明後，填這張卡。**填不出來的欄位，就是要去問監考或去讀程式找的地方。**

```
【題目理解卡】
題號 / 名稱：
一句話目標：

輸入：（來源、格式、範圍、大小）
輸出：（目的地、格式——精確到空白與換行）

評分方式：
  - 正確性怎麼判定：
  - 效能怎麼量（時間？吞吐量？延遲？cycle 數？）：
  - 給分方式（門檻制？依排名？依比例？）：
  - 提交方式與次數限制：

限制：
  - 時間 / 記憶體：
  - 硬體（哪個板子、哪個核心、時脈）：
  - 不能修改的檔案 / 介面：
  - 不能用的方法：

可以動的地方：
基準（baseline）：目前的程式表現如何？

疑點（要去確認的）：
  1.
  2.
```

### 給模型的提示

```
請根據以下題目說明，填寫「題目理解卡」（格式如下）。
規則：
- 每一欄只填題目明確寫到的；沒寫的填「未說明」，不要猜。
- 「疑點」欄列出你覺得最容易誤解、或會影響做法的地方。
- 特別注意評分方式和不能修改的範圍。

{{貼理解卡格式}}

題目：
{{貼題目}}
```

## 3. 階段三：系統架構圖（10–20 分鐘）

目標：畫出「誰跟誰說話、資料怎麼流、時間花在哪」。

### 3.1 要回答的問題

| 層次 | 問題 |
|---|---|
| 元件 | 有哪些獨立運作的單位？（process、ROS node、執行緒、核心、DMA channel、PIO state machine、中斷處理器）|
| 連接 | 元件之間怎麼溝通？（topic、FIFO、共享記憶體、DMA、中斷、函式呼叫）|
| 資料流 | 資料從哪進來、經過哪些轉換、從哪出去？每段的資料量與頻率？|
| 控制流 | 誰觸發誰？輪詢（polling）、中斷、計時器、事件驅動？|
| 同步 | 哪些資料被多個執行單位共用？用什麼保護？|
| 時間 | 哪一段最慢？哪一段在等待？哪些可以平行？|
| 資源 | 有限的資源有哪些？（DMA channel、PIO 指令記憶體 32 條、SM 數量、FIFO 深度、SRAM、CPU 核心）|

### 3.2 架構圖範例格式

```
[資料來源] --(格式, 頻率)--> [元件 A] --(機制)--> [元件 B] --> [輸出]
                                 |                     ^
                                 +----(共享 buffer, 鎖)-+

元件 A：責任 ___；執行於 ___（核心/執行緒/node）；觸發方式 ___
元件 B：...
瓶頸猜測：___（推測，待量測）
```

### 3.3 給模型的提示

```
/架構
根據目前讀到的題目和程式，畫出 ASCII 系統架構圖。
要求：
1. 標出每個元件、元件間的通訊機制、資料格式與頻率（不知道的標 ?）
2. 每個元件一行說明：責任、執行在哪、怎麼被觸發
3. 標出所有「共享資源」和保護方式
4. 標出你認為的效能瓶頸，並註明是【推測】還是有依據
5. 最後列出圖中還不確定、需要我去查證的地方

{{貼相關程式或說明}}
```

## 4. 階段四：精讀 datasheet / 技術文件段落

只讀題目會用到的部分。好的讀法順序：

1. **該章 Overview 與方塊圖**：這個周邊做什麼、由哪些部分組成。
2. **操作流程 / 程式設計模型**（Programmer's model）：要依什麼順序設定什麼。
3. **暫存器表**：只看會用到的欄位；注意 reset 預設值、讀寫屬性（RO/RW/WC 寫 1 清除）。
4. **限制與注意事項**：對齊、最大值、時序、errata。
5. **範例程式**：pico-examples、SDK 內的範例比文字更快理解。

### 4.1 讀長文件的技巧

- 一次貼一個小節（數百到兩千字），不要整章貼上，模型容易漏看。
- 先問「這段跟題目有沒有關係？可以跳過嗎？」節省時間。
- 數值（時脈、深度、數量、位元寬度）請模型列表，再自己對照原文確認。
- 用 PDF 檢視器的搜尋功能找關鍵字，比翻頁快很多：搜暫存器名、函式名、"must"、"note"、"errata"。

### 4.2 給模型的提示

```
/段落
以下是 {{文件名稱}} 的 {{章節}}。我正在做的題目是：{{一句話}}。
請輸出：
1. 三句話摘要：這段在講什麼
2. 重要的暫存器 / 欄位 / 參數表格（名稱、位元、意義、預設值、讀寫屬性）——只列原文有的
3. 正確的操作順序（步驟 1、2、3…）
4. 限制、陷阱、容易誤解的地方
5. 這段和我的題目有什麼關係；可以利用來優化的點
6. 讀完還不清楚、需要再查的地方
所有數值請保留原文寫法，不要換算或推論。

{{貼段落}}
```

## 5. 階段五：程式碼走讀

### 5.1 走讀順序

1. 從進入點（`main`）開始，只看主流程，跳過細節函式。
2. 找出主迴圈或主要處理流程（通常是效能熱點所在）。
3. 標出：初始化區、處理區、輸出區、同步點。
4. 再深入熱點函式。

### 5.2 有用的指令

```bash
grep -rn "函式名" .                     # 找定義與呼叫
grep -rn "^[a-z].*(" src/*.c | head     # 粗略列出函式定義
grep -rn "dma_\|pio_\|multicore_\|spin_lock\|mutex" --include='*.c' .   # 找用到哪些硬體/同步 API
grep -rn "create_subscription\|create_publisher\|create_timer" .        # ROS 2 的通訊介面
wc -l $(find . -name '*.c')             # 哪個檔案最大
```

### 5.3 給模型的提示

```
/走讀
以下是 {{檔名}}。請：
1. 說明整體結構（初始化 / 主流程 / 輸出），用縮排條列呼叫關係
2. 描述資料怎麼流過這段程式
3. 指出熱點：哪些迴圈或呼叫最可能耗時，理由是什麼
4. 指出可疑或可能有 bug 的地方
5. 指出用到的硬體或系統 API，以及各自的作用
不要提出修改，先只描述。

{{貼程式碼}}
```

## 6. 階段六：驗證理解

讀完之後，在動手前確認自己真的懂：

- **預測行為**：「如果把 X 改成 Y，會發生什麼？」先自己猜，再實際跑一次對照。
- **跑 baseline**：先把原始程式完整編譯、執行、（如果允許）提交一次，記錄基準分數與效能。這同時確認了整個工具鏈可以用。
- **請模型出題考你**：

```
根據我們剛才整理的架構，出 5 個問題考我是否真的理解這個系統
（包含：資料流、同步、效能瓶頸、硬體限制）。我回答後請批改。
```

## 7. 常見的讀題錯誤

| 錯誤 | 後果 | 預防 |
|---|---|---|
| 沒看評分腳本，只看文字說明 | 優化了不計分的部分 | 找 `.gitlab-ci.yml`、judge 腳本、測試檔 |
| 沒注意輸出格式細節 | 結果對但被判錯 | 對照範例輸出，逐字元比對（`diff`）|
| 誤會單位（位元組 vs 筆數、ms vs us、Hz vs 週期）| 數值差好幾倍 | 每個數值都寫上單位 |
| 改了不能改的檔案或介面 | 成績不計或編譯失敗 | 理解卡寫明「不能動的地方」|
| 沒先跑 baseline | 不知道優化有沒有效，也不知道環境能不能跑 | 動手前先跑一次 |
| 一開始就細讀 datasheet 全章 | 時間耗盡 | 只讀相關段落，先看圖與範例 |
| 相信模型說的 API 而沒查證 | 編譯錯誤或行為錯誤 | `grep` header 確認 |
