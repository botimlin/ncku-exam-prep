## 2.2 先懂這些概念

### 2.2.1 名詞

- **序列埠（serial port）**：電腦和 Pico 之間的一條「位元組管線」，一端寫進去的 byte 依序從另一端出來。Pico 用 USB 模擬序列埠（USB CDC），Linux 上叫 `/dev/ttyACM0`。USB CDC 不看 baudrate（`serial_bridge.py:44` 註解），但**不要設 1200**，SDK 會因此讓板子重開進 BOOTSEL（`pico/app_serial.c:66`）。
- **pty（虛擬終端機）**：Linux 用軟體做出來的一對序列埠（master / slave）。`fake_pico.py` 拿 master，你的程式開 slave（例如 `/dev/pts/5`），用起來跟 `/dev/ttyACM0` 一樣。
- **封包（frame）**：序列埠只會傳一串 byte，沒有「一筆資料」的邊界。所以要約定格式：開頭記號、長度、內容、檢查碼，接收端才切得出一筆一筆。
- **小端（little-endian）**：多位元組的數字「低位元組先送」。0x0008 送成 `08 00`。x86、ARM、RISC-V 都是小端。
- **CRC-32**：把整包內容算成一個 32 位元的檢查碼。傳輸中只要錯 1 個 bit，CRC 幾乎一定不同，接收端就知道這包壞了。
- **topic**：ROS 2 node 之間傳資料的「頻道」，有名字（`/number`）和固定的訊息型別（`std_msgs/msg/Int32`）。
- **QoS（Quality of Service）**：publisher 和 subscriber 各自設定的傳送規則（可靠 / 盡力、要不要保留舊資料）。兩端不相容時「連得上但收不到」。

### 2.2.2 封包格式（逐 byte）

兩邊的定義：電腦端 `frame.py:4-6`（docstring）、`frame.py:22-25`（`encode()`）；Pico 端 `pico/serial_proto.h:3-7`（格式註解）、`pico/serial_proto.c:92-101`（`proto_send()`）、`pico/serial_proto.c:39-76`（`proto_feed()`）。

```text
位移:   0      1      2      3      4       5       6 ............ 5+len   6+len  7+len  8+len  9+len
      +------+------+------+------+-------+-------+-----------------+------+------+------+------+
      | 0xAA | 0x55 | cmd  | seq  | len   | len   | payload         | crc  | crc  | crc  | crc  |
      |      |      | (u8) | (u8) | 低8位 | 高8位 | (len 個 byte)   | b0   | b1   | b2   | b3   |
      +------+------+------+------+-------+-------+-----------------+------+------+------+------+
      |<- sync ->|  |<------------ CRC-32 計算範圍：cmd 到 payload 結尾 ---->|<- crc32，小端 ->|
                                                                             (b0 = 最低位元組)
整包長度 = 10 + len。每包固定開銷 10 bytes。

實例（本次實測 python3 frame.py 的輸出）：ECHO, seq=7, payload="hi"
  aa 55 | 01 | 07 | 02 00 | 68 69 | ce 5e fd fb
  sync    cmd  seq  len=2   'h''i'  crc32 = 0xFBFD5ECE（小端送出）
```

| 欄位 | 位移 | 大小 | 意思 | `frame.py` | `pico/serial_proto.c` |
|---|---|---|---|---|---|
| sync | 0–1 | 2 B | 固定 `AA 55`，用來找封包開頭 | `HDR = b"\xAA\x55"`（`frame.py:16`） | `SYNC0`/`SYNC1`（`serial_proto.h:14-15`），收：`serial_proto.c:41-47`，送：`serial_proto.c:93` |
| cmd | 2 | u8 | 指令：`0x01` ECHO、`0x02` SUM_U32、`0x03` CRC32 | `frame.py:17` | `serial_proto.h:18-20` |
| seq | 3 | u8 | 序號，回覆會帶回同一個值，用來配對 | `seq & 0xFF`（`frame.py:24`） | `f->seq = hdr[1]`（`serial_proto.c:52`），回覆照抄（`app_serial.c:27,40,47`） |
| len | 4–5 | u16 小端 | payload 長度 | `struct.pack("<BBH", ...)`（`frame.py:24`） | `hdr[2] \| (hdr[3] << 8)`（`serial_proto.c:53`）；送出 `len & 0xFF, len >> 8`（`serial_proto.c:93`） |
| payload | 6 … 5+len | len B | 資料。SUM_U32 時是 u32 小端陣列 | `bytes(payload)`（`frame.py:24`） | `f->payload[idx++] = b`（`serial_proto.c:59`），4-byte 對齊（`serial_proto.h:29`） |
| crc32 | 最後 4 B | u32 小端 | 對 cmd..payload 算的 CRC-32 | `struct.pack("<I", zlib.crc32(body) & 0xFFFFFFFF)`（`frame.py:25`） | 收：`serial_proto.c:67-71`；送：`serial_proto.c:94-96` |

Pico 端兩個方向都是用位移一個 byte 一個 byte 組出來的（`serial_proto.c:53,67-68,93,96`），所以跟 CPU 的大小端無關；payload 裡的 u32 則是用 `memcpy` 直接當成 CPU 的 `uint32_t`（`app_serial.c:36,39`），依賴「ARM / RISC-V 都是小端」（`app_serial.c:39` 註解）。

### 2.2.3 CRC 的規格（CRC-32/ISO-HDLC，也就是 zlib 用的那一種）

| 參數 | 值 | Pico 端出處 | 電腦端 |
|---|---|---|---|
| 寬度 | 32 bit | — | `zlib.crc32` |
| 多項式 | 0x04C11DB7（反射寫法 0xEDB88320） | `serial_proto.c:18` | zlib 內建 |
| 位元順序 | 輸入、輸出都反射（LSB 先算，查表法右移） | `serial_proto.c:18,28` | zlib 內建 |
| 初值 | 0xFFFFFFFF | `serial_proto.c:27`（`crc ^= 0xFFFFFFFFu`，從 `crc=0` 呼叫） | zlib 內建 |
| 最後 XOR | 0xFFFFFFFF | `serial_proto.c:29` | zlib 內建 |
| 檢查值 `"123456789"` | 0xCBF43926 | `serial_proto.c:24` 註解 | `zlib.crc32(b"123456789")` |
| 計算範圍 | cmd、seq、len、payload（不含 `AA 55`，不含 crc 本身） | `serial_proto.c:69-70`、`94-95` | `frame.py:25`（`body` 不含 HDR） |

本次實測：C 端 `crc32_update(0, "123456789", 9)` 印出 `0xCBF43926`，Python `zlib.crc32(b"123456789")` 印出 `0xcbf43926`。

CRC 可以「接著算」：C 的 `crc32_update(crc, b, n)` 把上一段的結果當 `crc` 傳進去（`serial_proto.h:32`，`proto_send()` 就是先算 header 再接著算 payload，`serial_proto.c:94-95`）；Python 對應寫法是 `zlib.crc32(第二段, zlib.crc32(第一段))`（本次實測與整段一次算的結果相同）。

### 2.2.4 長度上限：三個數字不要搞混

| 名稱 | 值 | 在哪 | 意思 |
|---|---|---|---|
| `MAX_LEN` | 8192 | `frame.py:18` | 電腦端 `FrameParser` 收得下的最大 payload，**等於 Pico 的 `FRAME_MAX_PAYLOAD`**。`len` 比它大的包當壞包丟掉（2026-11-12 起；之前這個常數是 65535 而且沒被用到）。Pico 那邊改大，這裡也要改 |
| `FRAME_MAX_PAYLOAD` | 8192 | `pico/serial_proto.h:23` | Pico 收得下的最大 payload。`len > 8192` 的包在收完 header 時就被丟掉、不回覆（`serial_proto.c:54`） |
| `CHUNK_BYTES` | 4096 | `frame.py:19` | 電腦端「一包最多放幾 bytes」，給 `serial_bridge.py` 批次模式（`batch_size=0`）和 `multi_device.split()` 用。必須 ≤ `MAX_LEN`（8192） |

本次實測（把 Python 編好的封包串流餵給 PC 版的 `proto_feed()`）：len=8192 的包回傳 `OK`，len=8193 的包在第 6 個 byte（len 高位元組）就回傳 `-1`。電腦端 `encode()` 遇到 len ≥ 65536 會丟 `struct.error: 'H' format requires 0 <= number <= 65535`（本次實測）。

### 2.2.5 對齊（resync）：收到垃圾或壞包時怎麼辦

「對齊」是指：資料流中間混進了垃圾（printf 的文字、上次沒收完的半包），接收端要能自己找回下一個 `AA 55`。兩邊做法不一樣：

| 情況 | 電腦端 `FrameParser.feed()` | Pico 端 `proto_feed()` |
|---|---|---|
| 找開頭 | `buf.find(HDR)`，前面的垃圾全丟（`frame.py:52,56`） | 狀態機 `WAIT_AA → WAIT_55`（`serial_proto.c:41-47`） |
| `AA AA 55` | `find` 自然找到第二個 AA | 特別處理：在 `WAIT_55` 又看到 AA 就留在 `WAIT_55`（`serial_proto.c:46`） |
| 找不到 `AA 55` | 只留最後 1 byte（可能是半個 AA）（`frame.py:53-55`） | 停在 `WAIT_AA` |
| 長度太大 | `len > MAX_LEN`（8192）→ `bad_len += 1`，往後挪 1 byte 重新找 `AA 55`（`frame.py:60-63`，2026-11-12 加的） | `len > 8192` → 回 `-1`、回到 `WAIT_AA`，後面的 payload 當垃圾掃過（`serial_proto.c:54`） |
| CRC 錯 | `bad_crc += 1`，只往後挪 **1 byte** 再找 `AA 55`（`frame.py:72-74`） | 回 `-1`，整包已讀完，從下一個 byte 開始找（`serial_proto.c:65,71`） |
| 收一半就停了 | 每次 `transact()` 都建新的 parser（`frame.py:82`），舊的半包隨之丟掉 | 閒置 100 ms 且 `proto_busy()` → `proto_reset()`（`app_serial.c:73-74`） |

這個差異在 `pico/README.md:144` 已經記錄為「已知、實務上沒差」（USB 輸入方向有流量控制不會掉 byte，`pico/README.md:140`）。

本次實測（電腦端）：在一個好包前面塞一個假表頭 `AA 55 01 00 FF FF`（假裝 len=65535），`feed()` 馬上判定長度太大、往後挪，把後面的好包解出來：`[(1, 9, b'ok')] bad_len = 1`。修正前（`MAX_LEN` 沒被用到時）要再補滿 65545 bytes 才解得出來，長時間執行的 `fake_pico.py` 會因此卡住。

### 2.2.6 一次來回（transaction）的時序

```text
電腦 transact()                                  Pico (app_serial.c) / fake_pico serve()
 reset_input_buffer()  (frame.py:83)
 write(封包)  ──────── AA 55 cmd seq len payload crc ────────>  proto_feed() 逐 byte 收
 while 還沒到 deadline:                                           收完且 CRC 對 → handle(cmd)
   read(in_waiting or 1)  (frame.py:87)                           proto_send(同 cmd, 同 seq, 結果)
   parser.feed()  <──────── AA 55 cmd seq len 結果 crc ─────────
   cmd、seq 都對 → return payload  (frame.py:89-90)
 逾時 → 印「逾時，重試 k/3」再送一次 (frame.py:91)
 3 次都逾時 → raise TimeoutError (frame.py:92)
```

每一次來回都有固定開銷（系統呼叫、Python、USB 輪詢），跟資料多少無關。所以「包數越少越快」——這就是批次的意義（`serial_bridge.py:10-12`、`bench.py:5-6`）。

### 2.2.7 ROS 2 的 QoS 相容規則

`create_publisher(型別, topic, 10)` 的 `10` 等於預設 QoS：RELIABLE、VOLATILE、KEEP_LAST、depth 10（`node_template.py:22`）。兩端 QoS 不必完全一樣，但要「相容」：

| 發布端 \ 訂閱端 | 訂閱端 RELIABLE | 訂閱端 BEST_EFFORT |
|---|---|---|
| 發布端 RELIABLE | 收得到 | 收得到 |
| 發布端 BEST_EFFORT | **收不到** | 收得到 |

| 發布端 \ 訂閱端 | 訂閱端 VOLATILE | 訂閱端 TRANSIENT_LOCAL |
|---|---|---|
| 發布端 VOLATILE | 收得到 | **收不到** |
| 發布端 TRANSIENT_LOCAL | 收得到 | 收得到（晚加入也拿得到最後幾筆） |

口訣：**訂閱端要求的不能比發布端提供的多**。出處：`node_template.py:20-22`、`README.md:65-69`。depth（佇列長度）兩端不必一樣。不相容時兩邊都會印 `incompatible QoS` 警告，`Last incompatible policy:` 會告訴你是哪一項（`tools/debug-ros2.md:91-96`，該文件標為實測；本次沒有實測）。

## 2.3 逐檔說明

### 2.3.1 `frame.py`

#### 用途

封包格式的唯一定義（電腦端）。提供：組包 `encode()`、u32 陣列打包 `pack_u32()` / `unpack_u32()`、串流解析 `FrameParser`、送一包並等回覆 `transact()`、封包比對 `diff()`。不需要 ROS，不需要 pyserial（只有 `transact()` 需要一個已開好的 `serial.Serial` 物件）。

#### 怎麼編譯 / 執行

在 `預製程式碼/ros2/` 執行：

| 指令 | 做什麼 | 預期輸出 |
|---|---|---|
| `python3 frame.py` | 自我測試（`frame.py:133-153`） | `ECHO 'hi' = aa 55 01 07 02 00 68 69 ce 5e fd fb` 和 `frame.py 自我測試 OK` |
| `python3 frame.py diff "預期hex" "實際hex"` | 逐欄位比對兩個封包（`frame.py:126-131`） | 一張表格 + 第一個不同的欄位 + 線索 |

注意：`diff` 模式要**剛好 3 個參數**（`frame.py:126-129`）。少給或多給一個參數會印用法 `用法: python3 frame.py diff "預期 hex" "實際 hex"（兩個都要加引號）` 並結束（2026-11-12 起；之前會默默跑自我測試）。hex 字串可以有空白（`frame.py:106` 會先刪掉空白）。

#### 對外介面

| 名稱 | 參數 | 回傳 / 效果 | 注意 |
|---|---|---|---|
| `HDR` | — | `b"\xAA\x55"` | `frame.py:16` |

| `transact(ser, cmd, payload, seq=0, timeout=1.0, retries=3)` | `ser` 是 `serial.Serial(port, timeout=0.05)` | 回覆的 payload（bytes） | `frame.py:77-92`；全部逾時丟 `TimeoutError`；最慢 `timeout × retries` = 3 秒 |
| `split_fields(raw)` | 一包 bytes | `[(欄位名, bytes), ...]` | `frame.py:95-101`；payload 長度用「實際收到幾 byte」推算，不看 len 欄位 |
| `diff(exp_hex, act_hex)` | 兩個 hex 字串 | 印表格、第一個不同、線索 | `frame.py:104-123` |

#### 程式流程

`encode()`（`frame.py:22-25`）：

1. `struct.pack("<BBH", cmd, seq & 0xFF, len(payload))`：`<` = 小端、`B` = u8、`H` = u16，得到 4 bytes 的 cmd、seq、len。
2. 接上 payload 成為 `body`。
3. 回傳 `HDR + body + struct.pack("<I", zlib.crc32(body) & 0xFFFFFFFF)`：CRC 只算 `body`。

`FrameParser.feed(data)`（`frame.py:48-74`），每次呼叫都在 `while True` 裡盡量多解幾包：

1. `self.buf += data`，把新資料接在暫存後面（`frame.py:49`）。
2. 找 `AA 55`（`frame.py:52`）。找不到 → 只留最後 1 byte，回傳（`frame.py:53-55`）。
3. 丟掉 `AA 55` 前面的垃圾（`frame.py:56`）。
4. 不滿 6 bytes（表頭沒收齊）→ 回傳，等下次（`frame.py:57-58`）。
5. 讀 cmd、seq、len（`frame.py:59`）。`len > max_len`（預設 `MAX_LEN` = 8192）→ `bad_len += 1`，只刪 1 byte，回到步驟 2（`frame.py:60-63`，跟 Pico 一樣把它當壞包）。算整包長度 `6 + n + 4`（`frame.py:64`）；沒收齊 → 回傳（`frame.py:65-66`）。
6. 算 CRC 比對（`frame.py:67-69`）。對 → 把 `(cmd, seq, payload)` 加進輸出，從暫存刪掉整包（`frame.py:70-71`）。錯 → `bad_crc += 1`，只刪 1 byte，回到步驟 2 重新找（`frame.py:72-74`）。

`transact()`（`frame.py:77-92`），最多做 `retries` 輪：

1. 每輪建新的 `FrameParser`（`frame.py:82`），`ser.reset_input_buffer()` 清掉上次殘留的回覆（`frame.py:83`）。
2. 送出封包（`frame.py:84`），deadline = 現在 + `timeout`（`frame.py:85`）。
3. 迴圈：`ser.read(ser.in_waiting or 1)`——有多少讀多少，沒有就讀 1 byte 等 `ser.timeout`（0.05 s）（`frame.py:87`）；解出來的包裡找 **cmd 一樣且 seq 一樣** 的，找到就回傳 payload（`frame.py:88-90`）。cmd 或 seq 不對的包直接忽略。
4. 逾時 → 印 `[transact] cmd=0x.. seq=.. 逾時，重試 k/3`（`frame.py:91`），下一輪重送。
5. 全部失敗 → `TimeoutError("... 沒有回覆 (port 對嗎? Pico 有在跑嗎?)")`（`frame.py:92`）。

`diff()`（`frame.py:104-123`）：

1. 兩個 hex 轉 bytes，各自用 `split_fields()` 切欄位（`frame.py:106,109`）。
2. 逐欄位印 `| 欄位 | 預期 | 實際 | 相同? |`（`frame.py:107-112`），記下第一個不同的欄位（`frame.py:112`）。
3. 依序檢查 4 種線索（`frame.py:115-122`），印出來。

自我測試（`frame.py:133-153`）測 4 件事：一次餵 1 byte 也能解（半包）；垃圾 + 壞 CRC 包 + 兩個好包黏在一起、而且從中間切兩次餵，要剛好解出兩個好包且 `bad_crc == 1`；`pack_u32([1, 2, -1])` 解回 `[1, 2, 0xFFFFFFFF]`；len 超過 `MAX_LEN` 的包要丟掉、後面的好包照收（2026-11-12 加的）。

#### `diff` 的線索怎麼讀

| 線索（原文） | 判斷條件 | 意思 | 去哪修 |
|---|---|---|---|
| `實際有 0d 0a、預期沒有 → CRLF 轉換沒關` | 實際含 `0d 0a`、預期沒有（`frame.py:115-116`） | 有人把 `0a`（`\n`）改成 `0d 0a`（`\r\n`） | Pico：`stdio_set_translate_crlf(&stdio_usb, false)`（`app_serial.c:61`）、CMake `PICO_STDIO_DEFAULT_CRLF=0`（見第 3 章）；電腦：pty 要 raw（`fake_pico.py:68-69`） |
| `len 兩個 byte 對調 → 大小端顛倒` | 實際 len 等於預期 len 反過來（`frame.py:117-118`） | 有一邊用大端送 len | Python 的格式字串要 `<`；C 要低位元組先送（`serial_proto.c:93`） |
| `開頭不是 aa 55 → 混入文字（printf）或少收 / 錯位` | 實際前 2 byte 不是 `AA 55`（`frame.py:119-120`） | Pico 用了 `printf`，或讀到半包 | Pico 端不要 `printf`（`app_serial.c:6-7`） |
| `實際封包的 crc32 對不上它自己的內容` | 用 `a[2:-4]` 重算 CRC 跟最後 4 byte 不同（`frame.py:121-122`） | CRC 的範圍、規格或位元組順序錯了，或資料被改過 | 見下面「CRC 錯在哪」 |

`diff` 只會告訴你「CRC 不對」，不會告訴你**哪裡**不對。下面這段（本次在 scratchpad 寫來驗證、repo 裡沒有）可以直接貼進終端機，依序試「範圍 × 大小端 × 有沒有最後 XOR」：

```bash

a = bytes.fromhex(sys.argv[1].replace(" ", ""))
got = a[-4:]
for name, c in [("cmd..payload(正確範圍)", zlib.crc32(a[2:-4])), ("含 AA 55", zlib.crc32(a[:-4])), ("只算 payload", zlib.crc32(a[6:-4]))]:
    for en in "<>":
        for x in (0, 0xFFFFFFFF):
            if struct.pack(en + "I", c ^ x) == got:
                print("符合:", name, "小端" if en == "<" else "大端(位元組順序反了)", "少了最後 XOR" if x else "")
' "aa 55 02 01 08 00 0a 00 00 00 01 00 00 00 96 43 34 93"
```

本次實測 4 個樣本：正確封包 → `符合: cmd..payload(正確範圍) 小端`；最後 4 byte 每個都是正確值 XOR `ff` → `… 小端 少了最後 XOR`；最後 4 byte 順序反過來 → `… 大端(位元組順序反了)`；CRC 把 `AA 55` 也算進去 → `符合: 含 AA 55 小端`。什麼都沒印 = 不是這 12 種之一（例如初值不同、根本是別種 CRC），再對照 `algo/crc32.c`（見第 5 章）。

### 2.3.2 `serial_bridge.py`

#### 用途

一個 ROS 2 node（名字 `serial_bridge`，`serial_bridge.py:33`），把 topic 上收到的資料用 `frame.py` 的封包送給 Pico 算，再把結果發布到另一個 topic：

```text
/numbers (std_msgs/Int32MultiArray) --SUM_U32 (0x02)--> Pico --> /sum (std_msgs/UInt32)
/bytes   (std_msgs/UInt8MultiArray) --CRC32   (0x03)--> Pico --> /crc (std_msgs/UInt32)
```

（`serial_bridge.py:4-5`）

#### 怎麼編譯 / 執行

需要 ROS 2 Jazzy（rclpy）和 pyserial。在 `預製程式碼/ros2/` 開 3 個終端機（每個都先 `source /opt/ros/jazzy/setup.bash`）：

```bash
# 終端機 1：假 Pico（真板子就跳過這步，port 用 /dev/ttyACM0）
python3 fake_pico.py                     # 會印出 [fake_pico] fake0: /dev/pts/N
# 終端機 2：bridge
python3 serial_bridge.py --ros-args -p port:=/dev/pts/N -p batch_size:=0
# 終端機 3：看結果、送資料
ros2 topic echo /sum
ros2 topic pub --once /numbers std_msgs/msg/Int32MultiArray "{data: [1, 2, 3]}"   # /sum 應該出現 data: 6
ros2 topic pub --once /bytes std_msgs/msg/UInt8MultiArray "{data: [49, 50, 51]}"  # /crc 是 "123" 的 crc32
```

（指令出自 `serial_bridge.py:13-17`、`custom_msg_cheatsheet.md:37`；本次沒有 ROS 2，**沒有實測**。）啟動成功時 log 會印 `開啟 /dev/pts/N，batch_size=0`（`serial_bridge.py:52`）。

#### 文字 vs 二進位、一次一個 vs 批次

這支程式**沒有文字模式**。兩個模式都是二進位封包，差別只在一包放幾個數字。docstring 解釋為什麼文字慢（`serial_bridge.py:10-12`）：每次來回有固定開銷；文字 `"4294967295\n"` 要 11 bytes、u32 只要 4 bytes，而且 Pico 不用 `atoi`。把題目給的文字協定換成這支的二進位批次，見食譜 2.4.3。

| `batch_size` | 每包 payload | 20000 個數字幾包 | 真的 Pico（上限 8192） | `fake_pico.py` |
|---|---|---|---|---|
| `0`（預設） | 4096 B（1024 個數字） | 20 | 正常 | 正常（本次實測） |
| `1` | 4 B | 20000 | 正常但最慢 | 正常（本次實測） |
| `2`～`2048` | 8～8192 B | — | 正常（8192 剛好可以，`serial_proto.c:54` 用 `>`） | 正常（`frame.py` 的 `FrameParser` 也用 `>`） |
| `≥ 2049` | 開機時改成 2048（8192 B） | 10 | node 啟動時印 `[WARN] batch_size=… 太大，改成 2048（Pico 一包最多 8192 bytes）`，之後跟 2048 一樣（`serial_bridge.py:40-42`，2026-11-12 加的） | 同左（本次實測 2049、20000 都得到正確總和） |

#### CHUNK_BYTES 防呆（`on_bytes`）

CRC32 不能像加總一樣「切塊各算再合併」，因為 Pico 每一包都從頭算 CRC（`serial_bridge.py:77-78`）。所以 `on_bytes()` 先檢查：

```python
        if len(msg.data) > CHUNK_BYTES:
            self.get_logger().error(f"{len(msg.data)} bytes 超過一包上限 {CHUNK_BYTES}，CRC 不能分包算")
            return
```

（`serial_bridge.py:81-83`）本次實測：4096 bytes 正常回 CRC，4097 bytes 印 `[ERROR] 4097 bytes 超過一包上限 4096，CRC 不能分包算`，0 bytes 回 `crc32=0x00000000`。

注意這個上限是 4096，**比 Pico 收得下的 8192 嚴**：4097～8192 bytes 其實 Pico 算得了，但電腦端先擋掉了。要放寬：把 `CHUNK_BYTES` 改成 8192（但它同時影響批次模式和 `multi_device.py`），或食譜 2.4.7。

#### 執行緒模型

- `rclpy.spin(node)`（`serial_bridge.py:98`）用單執行緒 executor：callback **一個跑完才跑下一個**，所以 `on_numbers` 和 `on_bytes` 不會同時用序列埠（`serial_bridge.py:98` 註解），不需要鎖。
- 代價：一個 callback 在等 Pico 時，整個 node 都卡住。`batch_size=1` 加總 20000 個數字時，callback 要跑完 20000 次來回才會處理下一筆訊息。subscription 是 KEEP_LAST depth 10，等待期間如果湧入超過 10 筆，最舊的會被丟掉（依 QoS 定義推論，⚠️ 本次沒有實測）。
- 要平行用兩塊板子時，在 callback 裡開執行緒（`multi_device.run_parallel()`），見食譜 2.4.4。

#### 程式流程

1. `main()`：`rclpy.init()` → `SerialBridge()`（`serial_bridge.py:95-96`）。
2. `__init__`：宣告 4 個參數並讀出（`serial_bridge.py:34-39`）；開序列埠 `serial.Serial(port, timeout=0.05)`（`serial_bridge.py:45`）——port 錯會在這裡丟 `serial.SerialException`，node 起不來；建 2 個 publisher、2 個 subscription（`serial_bridge.py:48-51`）；印 log（`serial_bridge.py:52`）。
3. `rclpy.spin(node)` 開始等訊息（`serial_bridge.py:98`）。
4. `/numbers` 來了 → `on_numbers()`：
   1. `array.array("i", msg.data).tobytes()` 把 int32 陣列直接變成小端 bytes（`serial_bridge.py:62`）。負數的位元跟 u32 二補數一樣，所以 Pico 當 u32 加總結果正確。
   2. `step = 4 * batch`，或 `batch ≤ 0` 時 `CHUNK_BYTES // 4 * 4`（`serial_bridge.py:63`）。
   3. 每 `step` bytes 送一包 SUM_U32，回覆的 u32 累加並 `& 0xFFFFFFFF`（`serial_bridge.py:66-68`）。
   4. 任一包 `TimeoutError`（或拔線的 `SerialException`）→ log error，**整筆不發布**（`serial_bridge.py:69-71`）。
   5. 發布 `UInt32(data=total)`（`serial_bridge.py:72`），log `N 個數字, K 包, 總和=..., X ms`（`serial_bridge.py:73-74`）。
5. `/bytes` 來了 → `on_bytes()`：檢查長度（`serial_bridge.py:81-83`）→ 送一包 CRC32（`serial_bridge.py:85`）→ 逾時就 log 並 return（`serial_bridge.py:86-88`）→ 發布 `/crc`（`serial_bridge.py:89-91`）。
6. Ctrl+C 或外部關閉 → 關 port、`destroy_node()`、`try_shutdown()`（`serial_bridge.py:99-104`）。

### 2.3.3 `fake_pico.py`

#### 用途

沒有板子時，在電腦上假裝 1～N 塊 Pico。它用 `os.openpty()` 開虛擬序列埠，收 `frame.py` 格式的封包，照 Pico 的邏輯回覆（`fake_pico.py:4-6`）。用途是**先確定電腦端沒錯**：fake 上能動、真板子不能動 → 問題在 Pico 端或線路。

#### 怎麼編譯 / 執行

在 `預製程式碼/ros2/` 執行（只需要 Python 標準函式庫，不需要 pyserial）：

```bash
python3 fake_pico.py                                   # 1 個
python3 fake_pico.py -n 2 --link /tmp/ttyFAKE          # 2 個，另建捷徑 /tmp/ttyFAKE0、/tmp/ttyFAKE1
python3 fake_pico.py -n 2 --link /tmp/ttyFAKE --us-per-byte 1   # 模擬板子算得慢：每 byte 多 1 微秒
```

預期輸出（本次實測，`--link` 用 scratchpad 路徑，這裡縮寫成 `…/ttyFAKE`）：

```text
[fake_pico] fake0: /dev/pts/0  (捷徑 …/ttyFAKE0)
[fake_pico] fake1: /dev/pts/1  (捷徑 …/ttyFAKE1)
[fake_pico] 等待封包中... Ctrl+C 結束
```

它會一直跑，要另開終端機跑你的程式。`/dev/pts/N` 的 N 每次可能不同，所以多塊時用 `--link` 固定名字。結束：Ctrl+C 或 `kill`，捷徑會被刪掉（`fake_pico.py:82,89-93`；本次實測 `kill` 後捷徑消失）。

#### 對外介面

| CLI 參數 | 預設 | 意思 |
|---|---|---|
| `-n` | 1 | 開幾個假 Pico（`fake_pico.py:60`） |
| `--link` | `""` | 捷徑前綴；給了就建 `前綴0`、`前綴1`…（`fake_pico.py:61,72-77`） |
| `--us-per-byte` | 0.0 | 每收到 1 byte payload 多睡幾微秒，模擬計算時間（`fake_pico.py:62,51-52`） |

| 函式 | 參數 | 效果 |
|---|---|---|
| `handle(cmd, payload)` | cmd、bytes | ECHO 回原 payload；SUM_U32 回 u32 總和（mod 2^32）；CRC32 回 `zlib.crc32`；不認得回 `None`（`fake_pico.py:25-34`） |
| `serve(name, fd, us_per_byte)` | 名字、master fd、延遲 | 無窮迴圈：讀 → 解析 → `handle` → 回覆（`fake_pico.py:37-55`） |

#### 程式流程

1. 解析參數（`fake_pico.py:59-63`）。
2. 每個假 Pico：`os.openpty()` 開一對 pty（`fake_pico.py:67`）；兩端都 `tty.setraw()`（`fake_pico.py:68-69`），不然終端機的行規則會改掉 `0x0A`/`0x0D` 之類的 byte；slave fd 存在 `keep`，一直開著，否則你的程式關 port 時 master 會讀到 EIO（`fake_pico.py:65,70`）；印路徑、建捷徑（`fake_pico.py:71-78`）；開一條 daemon 執行緒跑 `serve()`（`fake_pico.py:80`）。
3. `serve()`：`os.read(fd, 65536)`（`fake_pico.py:42`）；`OSError` 時睡 0.05 秒重試（`fake_pico.py:43-45`）；每解出一包就 `handle()`（`fake_pico.py:46-47`）；不認得的 cmd 在**終端機**印 `[fake0] 不認得的 cmd=0x9，不回覆`，不寫進序列埠（`fake_pico.py:48-50`）；有 `--us-per-byte` 就睡 `len(payload) × us / 1e6` 秒（`fake_pico.py:51-52`）；`os.write` 寫到全部寫完（`fake_pico.py:53-55`）。
4. 主執行緒每秒睡一次，等 Ctrl+C 或 SIGTERM（`fake_pico.py:82-88`）。

#### 跟真 Pico（`pico/app_serial.c`）的差異

| 項目 | `fake_pico.py` | 真 Pico |
|---|---|---|
| payload 上限 | 8192，超過就丟、不回（`FrameParser` 的 `MAX_LEN`，2026-11-12 起） | 8192，超過就丟（`serial_proto.c:54`） |
| CRC 錯的包 | 丟掉，往後挪 1 byte | 丟掉，`n_bad++`（`app_serial.c:78`） |
| 收一半停住 | parser 一直沿用，等到收滿為止 | 閒置 100 ms 自動 `proto_reset()`（`app_serial.c:73-74`） |
| 不認得的 cmd | 不回，終端機印一行 | 不回，什麼都不印（`app_serial.c:54-55`） |
| 多塊平行 | 每塊一條 Python 執行緒；`--us-per-byte` 的 sleep 會放開 GIL，所以真的會同時；純 Python 計算部分受 GIL 限制 | 每塊獨立硬體 |
| 每次來回時間 | pty，本次實測幾十微秒（2.5） | USB，`ros2/README.md:29` 寫每包 ≥ 1 ms（⚠️ 本次沒有板子，未驗證） |

結論：**fake 上通過不代表真板子會過**，特別是速度、CRLF / printf、閒置重設。包大小上限兩邊現在一樣（8192）。

#### 要改的地方

| 行號 | 現在的值 | 意思 | 什麼情況要改、改成什麼 |
|---|---|---|---|
| `fake_pico.py:33` | `# TODO(改這裡) 題目若有新 cmd ...` | 新指令的運算 | 在 `return None` 前加 `if cmd == CMD_XXX: return ...`，邏輯要跟 Pico 端 `app_serial.c` 的 `handle()` 一致；`fake_pico.py:22` 的 import 也要加新常數（食譜 2.4.6） |

#### 實際執行輸出

見上面「預期輸出」，以及 2.3.4、2.3.5、2.3.2 都是對它跑的。對不認得的 cmd（0x09），本次實測電腦端：

### 2.3.5 `multi_device.py`

#### 用途

「split → send → gather」：把一大份資料切成很多塊，N 個序列埠（N 塊板子）各開一條執行緒，從共用佇列搶工作，做完把結果放回 `results[塊編號]`，最後依順序合併（`multi_device.py:2-6`）。快的板子會多做幾塊。不需要 ROS。

#### 怎麼編譯 / 執行

在 `預製程式碼/ros2/`，需要 pyserial：

```bash
# 終端機 1
python3 fake_pico.py -n 2 --link /tmp/ttyFAKE --us-per-byte 1
# 終端機 2
python3 multi_device.py /tmp/ttyFAKE0 /tmp/ttyFAKE1
# 真的板子
python3 multi_device.py /dev/ttyACM0 /dev/ttyACM1
```

（`multi_device.py:8-11`）給 2 個以上 port 時，它會先只用第 1 個跑一次，再用全部跑一次，方便比較（`multi_device.py:83`）。

#### 對外介面

| 函式 | 參數 | 回傳 / 效果 | 注意 |
|---|---|---|---|
| `split(data, chunk_bytes=CHUNK_BYTES, align=4)` | bytes | list of bytes，每塊 ≤ `chunk_bytes` 且是 `align` 的倍數 | `multi_device.py:24-27`；`align=4` 保證 u32 不會被切一半 |
| `worker(port, jobs, results, cmd, stats)` | — | 執行緒主體：開 port，`get_nowait()` 拿工作直到佇列空，`transact(seq=idx)`，失敗放 `None` | `multi_device.py:30-48`；一塊失敗會等 3 秒 |
| `run_parallel(ports, chunks, cmd)` | port list、chunk list、cmd | 依 chunk 順序的回覆 payload list；任何一塊失敗丟 `RuntimeError` | `multi_device.py:51-66`；會印「每個 port 做了幾塊」 |
| `merge_sum(replies)` | 回覆 list | 全部 u32 加總 mod 2^32 | `multi_device.py:69-72`；`TODO(改這裡)`：依題目換合併方式 |

#### 程式流程

1. 主程式：port 取自命令列（`multi_device.py:76`）；產生 200000 個隨機 u32（`multi_device.py:77`），打包成 800000 bytes（`multi_device.py:78`），切成 196 塊（`multi_device.py:79`），先在電腦上算好正確答案（`multi_device.py:80`）。
2. `run_parallel()`：所有 `(編號, chunk)` 放進 `queue.Queue`（`multi_device.py:53-55`）；結果陣列先填 `None`（`multi_device.py:56`）；每個 port 一條執行緒（`multi_device.py:58-62`）。
3. `worker()`：自己開 port（`multi_device.py:32`）；佇列空了就結束（`multi_device.py:36-39`）；`results[idx] = transact(...)`（`multi_device.py:41`）；`TimeoutError` → 印錯並放 `None`（`multi_device.py:42-44`）；結束時關 port、記錄做了幾塊（`multi_device.py:46-48`）。
4. 全部 join 後，有 `None` 就丟 `RuntimeError`（`multi_device.py:64-65`）。
5. `merge_sum()` 合併、跟正確答案比對、印時間（`multi_device.py:85-87`）。

為什麼順序一定對：每塊的結果寫在 `results[自己的編號]`，跟誰先做完無關（`multi_device.py:6`）。

#### 要改的地方

| 行號 | 現在的值 | 意思 | 什麼情況要改、改成什麼 |
|---|---|---|---|
| `multi_device.py:70-72` | `merge_sum`：`sum(...) & 0xFFFFFFFF` | 合併方式 | 最大值：`max(unpack_u32(r)[0] for r in replies)`；排序：`list(heapq.merge(*[unpack_u32(r) for r in replies]))`；CRC32：不能相加，要整份一次算，或協定加起始值（食譜 2.4.7） |

| `multi_device.py:77` | `[random.getrandbits(32) for _ in range(200_000)]` | 測試資料 | 換成題目的資料（讀檔、讀 topic） |

#### 實際執行輸出

本次實測，2 個假 Pico、`--us-per-byte 1`（port 路徑縮寫）：

```text

  每個 port 做了幾塊: {'…/ttyFAKE0': 196}
```

重跑一次：885.1 ms → 439.4 ms。`--us-per-byte 0`（純傳輸、沒有模擬計算）：29.3 ms → 17.6 ms、28.5 ms → 18.8 ms。

#### 常見錯誤

| 症狀 | 原因 | 修法 |
|---|---|---|
| 2 個 port 沒比 1 個快 | 瓶頸在電腦端 Python 或只有一塊板子真的在算 | 看「每個 port 做了幾塊」是不是平均；用 `--us-per-byte` 模擬確認程式本身能平行 |
| `RuntimeError: 有 chunk 失敗` | 某塊 3 次逾時 | 看上面印的 `[port] chunk i 失敗`；檢查 chunk 大小 ≤ Pico 上限 |
| 答案 `正確=False` | 合併方式不對，或 chunk 沒對齊 4 bytes | `split(..., align=4)`；檢查 `merge_*` |
| 某個 port 的 traceback 但答案正確 | 那個 port 開不起來，其他 port 代勞 | 修 port 路徑；不修也能交，但沒有加速 |

### 2.3.7 `custom_msg_cheatsheet.md`

#### 用途

#### 重點整理

- 先問：真的要自訂嗎？一串數字或 bytes 用內建的（`custom_msg_cheatsheet.md:3-13`）：

| 資料 | 型別 | Python 的 `msg.data` |
|---|---|---|
| 一串 bytes | `std_msgs/msg/UInt8MultiArray` | `array.array('B')` |
| 一串 int32 | `std_msgs/msg/Int32MultiArray` | `array.array('i')` |
| 一串 uint32 / float | `UInt32MultiArray` / `Float32MultiArray` | `array('I')` / `array('f')` |
| 一個數字 | `Int32`、`UInt32`、`Float64` | int / float |
| 文字 | `String` | str |
| 影像 | `sensor_msgs/msg/Image` | `array('B')` |

- 不要用 `ByteMultiArray`，它的 `data` 在 Python 是一個一個 bytes 物件的 list，很慢（`custom_msg_cheatsheet.md:15`）。
- `ros2 interface show` 說 MultiArray deprecated 只是建議，Jazzy 能用；`layout` 可以留空（`custom_msg_cheatsheet.md:16-17`）。
- 快的打包：`array.array('i', m.data).tobytes()` 直接得到小端 bytes 丟給 Pico；反方向 `vals = array.array('i'); vals.frombytes(raw)`（`custom_msg_cheatsheet.md:29-31`）。慢的：一個一個 `int()`、for 迴圈 append（`custom_msg_cheatsheet.md:33`）。

- 常見錯誤（`custom_msg_cheatsheet.md:80-84`）：沒 source → `ModuleNotFoundError`；檔名小寫開頭 → `rosidl_generate_interfaces` 出錯；固定長度陣列給錯長度，設定當下不報錯、publish 時才出事（該文件寫「實測 Jazzy」，本次沒有實測）；改了 `.msg` 要重開所有用到的 node。

### 2.4.1 topic 名稱打錯（官方練習 2-1 的典型 bug）

題目長這樣：「系統跑起來沒有錯誤訊息，但 `/double` 一直沒有資料。」

2. `ros2 topic list -t` → 看到 `/number`、`/numbr`（或 `/double`、`/doubel`）兩個很像的 topic。
3. `ros2 topic info /number` → `Publisher count: 1`、`Subscription count: 0`；`ros2 topic info /numbr` → `Publisher count: 0`、`Subscription count: 1`。訂閱端拼錯。
4. `ros2 node info /processor` → 確認是哪個 node 訂閱了錯的名字。

### 2.4.7 CRC32 的資料超過一包

`on_bytes()` 會擋下 > 4096 bytes 的資料（`serial_bridge.py:81-83`）。三種解法：

- **最快**：電腦端自己 `zlib.crc32(data)`，不送 Pico——只有題目不要求「由 Pico 算」時能用。
- **方案 (a)**：Pico 的 `FRAME_MAX_PAYLOAD`（`serial_proto.h:23`）加大，`CHUNK_BYTES`（`frame.py:19`）跟著加大到 ≥ 資料大小。上限是 len 欄位的 65535。注意 `CHUNK_BYTES` 也會改變批次模式和 `multi_device` 的切塊大小。
- **方案 (b)**（`serial_bridge.py:80`）：協定改成 payload 前 4 bytes 放「上一段的 crc」，Pico 算 `crc32_update(prev, data, n)`（`serial_proto.h:32` 本來就支援接著算）；電腦端每次把上一包回覆的 crc 放進下一包。`fake_pico.py` 對應寫法是 `zlib.crc32(data, prev)`。這是設計草稿，**沒有實測**。

## 2.7 一頁速查表

**封包**

```text
AA 55 | cmd(u8) | seq(u8) | len(u16 LE) | payload[len] | crc32(u32 LE)
CRC-32/ISO-HDLC (zlib)：poly 0xEDB88320(反射) init 0xFFFFFFFF xorout 0xFFFFFFFF check("123456789")=0xCBF43926
CRC 範圍 = cmd..payload（不含 AA 55）。整包 = 10 + len bytes。
cmd：01 ECHO　02 SUM_U32（回 u32 總和 mod 2^32）　03 CRC32（回 u32）
例：ECHO seq=7 "hi" = aa 55 01 07 02 00 68 69 ce 5e fd fb
```

**函式簽名**

```python
encode(cmd, seq, payload=b"") -> bytes
pack_u32(values) -> bytes            unpack_u32(data) -> list[int]
FrameParser().feed(data) -> [(cmd, seq, payload), ...]
transact(ser, cmd, payload, seq=0, timeout=1.0, retries=3) -> bytes   # 失敗 TimeoutError
split(data, chunk_bytes=CHUNK_BYTES, align=4) -> list[bytes]
run_parallel(ports, chunks, cmd) -> list[bytes]                        # 失敗 RuntimeError
merge_sum(replies) -> int
```

**ROS 2 除錯順序**：`node list` → `node info` → `topic list -t` → `topic info`（count）→ `topic info -v`（QoS）→ `topic echo` → `topic pub --once`。

**QoS**：發 BEST_EFFORT + 收 RELIABLE = 收不到；發 VOLATILE + 收 TRANSIENT_LOCAL = 收不到；其他組合都可以。

**常見錯誤**

| 症狀 | 先查 |
|---|---|
| `ros2: command not found` | `source /opt/ros/jazzy/setup.bash` |
| `No module named 'serial'` | `apt install python3-serial` |
| `could not open port` | `ls /dev/ttyACM*`、權限、Docker `--device`、別的程式占用 |
| 一直 `逾時，重試` | fake_pico 先測；包 ≤ 8192；Pico 沒有 printf；`frame.py diff` |
| `pub --once` 不結束 | 沒人訂閱 → topic 名字 |
| count 都 ≥ 1 但收不到 | QoS（`topic info -v`） |
| fake 上 OK、真板子不行 | 包大小 > 8192、CRLF、printf、速度 |
| 回覆數字怪 | 大小端（`<` / `memcpy`） |
