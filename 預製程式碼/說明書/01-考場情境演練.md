## 1.0 怎麼用這一章

這一章不是逐檔說明（那是第 2～8 章的工作），而是「考試當天拿到題目以後，手要怎麼動」。

- **1.1** 是開考後前 30 分鐘一定要做的事，不管題目是什麼都先做。
- **1.2～1.19** 每一節對應 `預製程式碼/預測考題.md` 的一個猜題編號（1-A、1-A'、1-B、1-C、2-1-A～C、2-2-A～E、2-3-A～F）。每一節的格式固定：
  1. **題目可能長這樣**：我自己編的假想題目，**不是**真的考題，只是讓你練習判斷。
  2. **判斷依據**：題目或 repo 裡出現哪些字，就代表是這一型。
  3. **要打開的檔案、先讀哪幾行**：`檔名:行號`，用 `grep -n` 對過（commit d102c17）。行號跑掉時，用旁邊寫的函式名稱或字串搜尋。
  4. **步驟**：改哪一行、改前 → 改後、怎麼編譯 / 執行、成功的樣子。
  5. **怎麼驗證**：跟電腦端的標準答案比對。
  6. **先交一版的最小做法 vs 之後的優化**。
  7. **常見陷阱**。
  8. **要貼給考場小模型的卡**：`prompt工具包/cards/` 裡的檔名和卡片標題（都核對過存在）。
- **1.20** 是 09:10–16:30 的時間分配範例，**1.21** 是交卷前檢查清單，**1.22** 是本章實測環境與發現的問題。

## 1.1 開考前 30 分鐘的固定流程

**目的**：在動任何程式之前，先知道「題目 repo 長什麼樣、CI 怎麼評分、環境能不能編譯燒錄」。這 30 分鐘做完，之後每一題都能直接進入修改。對應的提示卡是 `prompt工具包/cards/10-exam-day-flow.md` 的【提示卡｜開考 1/5】到【開考 5/5】，開場先貼 `prompt工具包/cards/00-starter.md` 的【開場｜1/3｜角色與規則】。

### 步驟 0（09:00–09:10，題目說明時）：只聽、只抄

- 抄下：題號、配分、每題的 commit message 或分支規定、哪些檔案不能改、評分看什麼（正確性？時間？）。
- 有聽不懂的規定，09:10 前舉手問。

### 步驟 1：clone、先打一個 tag

在你的工作資料夾（題目會說是哪裡）：

```bash
git clone <題目給的 GitLab 網址> exam && cd exam
git log --oneline -5          # 看出題者留下的 commit
git tag start                 # 隨時可以用 git diff start 看自己改了什麼
```

`git tag start` 的用法出自 `預製程式碼/tools/README.md:40`（考場工具 SOP 第 1 步）。

### 步驟 2：讀 repo 結構和 README

```bash
find . -maxdepth 3 -not -path './.git' -not -path './.git/*' -not -path '*/build/*' | sort | head -100
```

這行指令照抄【提示卡｜開考 1/5｜repo 結構地圖】。不要用 `-not -path './.git*'`：那樣會把 `.gitlab-ci.yml` 也藏掉（卡片檔頭的注意事項）。

要找的東西：

| 看到 | 代表 |
|---|---|
| `package.xml`、`*.launch.py`、`setup.py` | ROS 2 套件（要 `colcon build`），看第 2 章、`tools/cmake.md` §5 |
| `pico_sdk_import.cmake`、`*.pio`、`CMakeLists.txt` 裡有 `pico_sdk_init()` | pico-sdk 專案，看第 3 章 |
| `libmicroros/`、`pico_uart_transport.c` | micro-ROS，看第 4 章與 1.3 |
| `Makefile` + 一般 `.c` | 純 Linux C，看第 7 章 |
| `judge`、`test`、`expected`、`*.sh` | 評分用，通常不能改 |

### 步驟 3：讀 `.gitlab-ci.yml`（評分方法就寫在這裡）

```bash
wc -l .gitlab-ci.yml; sed -n 1,80p .gitlab-ci.yml
grep -nE "CI_COMMIT_MESSAGE|CI_COMMIT_BRANCH|rules:|only:|except:|if:" .gitlab-ci.yml
```

要抄到紙上的 7 件事（照【提示卡｜開考 2/5｜評分流程（.gitlab-ci.yml）】的 7 格）：stages 與 job 名稱、每個 job 的 image、觸發條件（commit message / 分支）、建置指令、怎麼判分、本地重現指令、不能改的檔名 / target / 輸出格式。

**commit message 格式**：2024 年是「CI 依 commit message 判斷題號」（`預測考題.md`）。今年的格式**現在不知道**，要從 `rules:` 裡的 `$CI_COMMIT_MESSAGE =~ /.../` 或題目說明看。11/13 試前測試時先記下來。下面的寫法只是格式示意（⚠ 假想，不是真的規定）：

```bash
git commit -m "<照 .gitlab-ci.yml 規定的題號字串> 修好 /double 沒資料"
```

### 步驟 4：確認 pico-sdk 版本

SDK 版本會影響某些 API 有沒有（例如 `dma_encode_transfer_count()` 2.2.0 才有，`pico/app_dma.c:21-24` 已經替 2.0/2.1 補上）。兩種查法：

```bash
# A. 已經 cmake configure 過一次（build 資料夾裡會自動產生）
cat build/generated/pico_base/pico/version.h | grep VERSION
# B. 還沒 configure：直接看 SDK
grep -E "^\s*set\(PICO_SDK_VERSION_(MAJOR|MINOR|REVISION)" $PICO_SDK_PATH/pico_sdk_version.cmake
```

實際執行輸出（本容器，pico-sdk 2.2.0 與 2.1.1 各查一次）：

```text
$ grep VERSION_STRING $S/ch01/pclean/generated/pico_base/pico/version.h
#define PICO_SDK_VERSION_STRING   "2.2.0"
$ grep -E "^\s*set\(PICO_SDK_VERSION_(MAJOR|MINOR|REVISION)" $S/pico-sdk/pico_sdk_version.cmake
    set(PICO_SDK_VERSION_MAJOR 2)
    set(PICO_SDK_VERSION_MINOR 2)
    set(PICO_SDK_VERSION_REVISION 0)
$ grep -E "^\s*set\(PICO_SDK_VERSION_(MAJOR|MINOR|REVISION)" $S/sdk211/pico_sdk_version.cmake
set(PICO_SDK_VERSION_MAJOR 2)
set(PICO_SDK_VERSION_MINOR 1)
set(PICO_SDK_VERSION_REVISION 1)
```

版本差異要注意的地方（審查時找到的，細節見第 3 章與第 6 章）：

| 版本 | 差異 |
|---|---|
| 2.0 / 2.1 | 沒有 `dma_encode_transfer_count()` → `app_dma.c`、`app_dma_pio.c` 已用 `#if PICO_SDK_VERSION_MINOR < 2` 補上 |
| 2.3.1 起 | RISC-V 預設加 `-mstrict-align` |
| 2.3.x | RISC-V 會自動選 `-march` |

### 步驟 5：確認板子插著、是哪一個序列埠

```bash
ls /dev/ttyACM* /dev/serial/by-id/
python3 -m serial.tools.list_ports
```

- 有幾片板子就應該有幾個 `ttyACM`；Debug Probe 也會占一個（`tools/debug-pico.md` §3）。
- `by-id` 的名字含序號，拔插後不會變；`ttyACM0/1` 的順序會變（`micro-ros/agent_cheatsheet.md` §2）。
- 容器裡看不到 → 容器要用 `--device /dev/ttyACM0` 或 `--privileged` 啟動（`ros2/README.md:23`）。權限不足 → `sudo chmod 666 /dev/ttyACM0`（`micro-ros/agent_cheatsheet.md:52`）。

本容器沒有板子，實際輸出是：

```text
$ ls /dev/ttyACM*
ls: cannot access '/dev/ttyACM*': No such file or directory
```

```bash

grep -nE "error|warning" build.log | head      # 看第一個 error
```

（`tools/README.md:44`，SOP 第 5 步。）

## 1.2 情境 1-A：ROS 2 把資料送到 Pico 算再收回，先修傳輸 bug，再改成二進位 + 批次（★★★）

### 題目可能長這樣（假想範例，不是真的考題）

> repo 裡有 `host/bridge.py`：訂閱 `/numbers`（`std_msgs/Int32MultiArray`），每個數字用 `ser.write(f"{v}\n".encode())` 一行一行送給 Pico；Pico 端 `firmware/main.c` 用 `scanf("%d")` 讀、加總後 `printf("%u\n", sum)` 回傳；`bridge.py` 把結果發到 `/sum`（`std_msgs/UInt32`）。
> (1) 現在 `/sum` 沒有輸出，請修好。(2) judge 會送 20000 個數字，越快完成分數越高。

### 判斷依據

- 有 `serial.Serial(...)`、`/dev/ttyACM*`、Pico 端 `stdio_usb`、`getchar` / `scanf` / `printf`。
- 題目說「傳輸」「加速」「轉成 binary」「一次傳很多筆」。
- 2025 年第 1 題就是這個骨架（ROS 2 送資料給板子跑 eBNN，資料轉 binary 加速傳輸，`預測考題.md` 表格）。
- 如果 repo 有 `libmicroros/` → 改看 1.3。

### 步驟 1：先讓原本的程式能動（第一版要交的就是這個）

**做什麼**：不要一開始就重寫。先找出「為什麼 `/sum` 沒輸出」，用最小改動修好，交一版拿次序分。

依序檢查（每一項都有對應的證據去看）：

| # | 檢查 | 指令 / 看哪裡 | 常見修法 |
|---|---|---|---|
| 1 | port 對不對 | `ls /dev/serial/by-id/`；程式裡的 port 字串 | 改成實際的 `ttyACM` |
| 2 | 有沒有別的程式開著同一個 port | `sudo lsof /dev/ttyACM0`（`micro-ros/agent_cheatsheet.md` §3） | 關掉 minicom / screen / 另一個 bridge |

### 常見陷阱

- **`CHUNK_BYTES` 一定要 ≤ `FRAME_MAX_PAYLOAD`**（`frame.py:19` 的註解）。Pico 收到 `len > 8192` 的封包會直接丟掉、不回覆（`serial_proto.c:54`），電腦端只會看到 3 次逾時。
- **`batch_size` 最大 2048**：`serial_bridge.py:60` 是 `step = 4 * self.batch`，2049 就是 8196 bytes > 8192，Pico 默默丟掉。**`fake_pico.py` 不檢查長度**（`fake_pico.py:25-34` 的 `handle()` 沒有長度限制），所以在 fake 上 2049 也會「成功」——fake 測過不代表真板子會過。
- CRC32 不能切包後相加：`serial_bridge.py:78` 會擋掉超過 `CHUNK_BYTES` 的 `/bytes` 訊息。（`pico/README.md:143` 那一列寫「沒有切包…未改」已經過時：程式現在會先擋下來、印錯誤，見 1.22。）
- 負數：`Int32MultiArray` 的 -1 送過去是 `0xFFFFFFFF`，總和是 mod 2^32（`frame.py:28-30` `pack_u32` 的註解）。題目要有號結果時，電腦端要自己轉回有號。
- `seq` 只有 8 bit，`frame.py:24` 會 `& 0xFF`。一次只有一包在路上（`transact()` 等到回覆才送下一包），所以繞回沒關係。
- 同一時間只能一個程式開序列埠（`tools/debug-pico.md` §3）。監看程式開著，bridge 會讀不到。
- Pico 端 USB 沒被電腦打開（DTR=0）時輸出會被直接丟掉（`serial_proto.c:85-87` 的註解）。

3. `step()` 的 `OP_IMM`（`:87`）同樣加。改前：

```c
    case OP_IMM:   if (F3(x) == 0) { c->x[rd] = a + imm_i(x); break; } return -1;
```

改後：

```c
    case OP_IMM:   if (F3(x) == 0) { c->x[rd] = a + imm_i(x); break; }
```

- 每加一條指令，就用 `riscv64-unknown-elf-as` + `objdump -M no-aliases,numeric` 拿標準答案，寫成 `CHECK`（`bits-riscv/README.md:36`）。

### 先交一版的最小做法 vs 之後的優化

- 第一版：照題目要的指令逐條加進 `switch`，每條一個 `CHECK`。

### 常見陷阱

- B 型、J 型立即值的位元是打亂的，最低位一定是 0（`:8-11`）。照 `imm_b()` / `imm_j()` 抄，不要自己重排。

## 1.14 情境 2-3-A：雙核心共用資料出現 race condition → 加鎖修好（★★★）

### 判斷依據

- 「兩顆核心」「共用變數 / 陣列」「結果每次不一樣、總是少一些」「race」「臨界區」「spinlock」。
- 官方練習 `section2-3` 的 critical-section：兩個執行緒各加 20000 次，沒鎖時少掉（`考試相關資訊/section2-3/README.md`）。

### 要打開的檔案、先讀哪幾行

| 檔案 | 先讀 |
|---|---|
| `考試相關資訊/section2-3/critical-section/main.c` | `:56-65`（沒鎖：讀、加、寫拆開）、`:68-77`（短鎖）、`:80-89`（長鎖） |
| `預製程式碼/pico/app_multicore.c` | `:7-11`（鎖怎麼選）、`:27-30`（共用變數、鎖）、`:32-49` `add_many()`（三種模式 + 「更快的做法」註解）、`:92-93`（建鎖）、`:98-111`（三種模式各跑一次） |
| `預製程式碼/pico/README.md` | `:79`（volatile 不是原子）、`:83-84`（臨界區要短、RP2350 spinlock 勘誤） |

### 步驟

1. **找出所有兩核都會寫的變數**，列成表（變數、誰寫、誰讀）。這就是【提示卡｜實作 6/9｜雙核分工：共享變數表 → 保護方式】要你填的東西。
2. **最小修法：每次更新都上鎖**。照 `app_multicore.c:37-39` 的寫法：

```c
            uint32_t save = spin_lock_blocking(lock);  // 拿鎖（同時關中斷）
            counter++;                     // ✅ 臨界區：只放「一定要保護」的那一行
            spin_unlock(lock, save);       // 放鎖（恢復中斷）
```

套到假想題目（假想程式，不是 repo 裡的檔案）：

```c
// 改前（兩核都跑這個迴圈）
for (uint32_t i = lo; i < hi; i++) hist[data[i]]++;
// 改後（最小修法）
for (uint32_t i = lo; i < hi; i++) {
    uint32_t s = spin_lock_blocking(lock);
    hist[data[i]]++;
    spin_unlock(lock, s);
}
```

鎖要先建好：`lock = spin_lock_init((uint)spin_lock_claim_unused(true));`（`app_multicore.c:92`）。

3. **更快的修法：各算各的，最後只鎖一次合併**（`app_multicore.c:46-48` 的註解）：

```c
static uint32_t hist_core[2][256];               // 每顆核心一份，放全域（core1 stack 只有 2 KB）
// 每顆核心：for (...) hist_core[core][data[i]]++;   ← 不用鎖
// 兩核都做完後（用 FIFO / queue 通知），core0 合併：
for (int v = 0; v < 256; v++) hist[v] = hist_core[0][v] + hist_core[1][v];
```

## 1.16 情境 2-3-C：用 DMA 取代 CPU 複製；修「count 填成 bytes」「沒 unclaim」「size 不對齊」（★★★）

### 題目可能長這樣（假想範例）

> `copy_block(dst, src, nbytes)` 用 DMA 搬 32-bit 資料，但搬完後 `dst` 後面的記憶體被蓋掉；而且呼叫第 17 次以後就拿不到通道。請修好，並比 CPU 迴圈快。

### 判斷依據

- 「DMA」「傳輸引擎」「count」「transfer size」「increment」「claim / unclaim」「對齊」。
- 官方練習 transfer-engine 的四個重點：`count` 是筆數不是位元組、位址遞增是描述的一部分、每筆大小只能 1/2/4 且要對齊、通道有限要取得歸還（`section2-3/README.md`）。

### 要打開的檔案、先讀哪幾行

| 檔案 | 先讀 |
|---|---|
| `考試相關資訊/section2-3/transfer-engine/engine.h` | `:17-29`（4 個通道、`count` 是 transfers、`xfer_size_t`） |
| `考試相關資訊/section2-3/transfer-engine/main.c` | part 3（`--mistake`：把 bytes 當 count） |

### 官方 transfer engine ↔ pico-sdk 對照

| 官方練習（`engine.h`） | pico-sdk 2.2.0（`hardware/dma.h`） |
|---|---|
| `engine_claim()`，沒有回 -1 | `dma_claim_unused_channel(false)`，沒有回 -1（`dma.h:118`） |
| `engine_job_t.size` = `XFER_8/16/32` | `channel_config_set_transfer_data_size(&c, DMA_SIZE_8/16/32)` |
| `src_increment` / `dst_increment` | `channel_config_set_read_increment` / `_write_increment` |

### 步驟

1. **先在電腦上看 count 錯的現象**。實際執行輸出（本容器，複製官方 `section2-3` 到 `$S/ch01/demo23` 後 `make mistake`）：

```text

   -> the engine moved 16384 words and wrote 12288 past the 4096 you meant
   nothing complained: the engine did exactly what you described.
```

2. **修 count**：bytes → 筆數。假想 bug（改前 → 改後）：

```c
dma_channel_configure(ch, &c, dst, src, nbytes, true);                                   // 改前：錯，搬了 4 倍
dma_channel_configure(ch, &c, dst, src, dma_encode_transfer_count(nbytes / 4), true);    // 改後：32-bit → nbytes/4 筆
```

`app_dma.c:6`：「count 是『傳輸次數』不是 bytes！搬 N bytes 用 32-bit → count = N/4」。RP2350 的 count 只有低 28 bits，高 4 bits 是 MODE，所以一律包 `dma_encode_transfer_count()`（`app_dma.c:10-12`）。

3. **修寫位址遞增**：預設設定是「讀遞增、寫**不**遞增」（`app_dma.c:14-15`）。memory → memory 複製一定要加：

```c
    channel_config_set_write_increment(&c, true);                       // ⚠ copy 一定要開寫遞增！
```

（`app_dma.c:131`，這是設計審查時修過的真 bug，`pico/README.md:100`。）

4. **修沒 unclaim**：每次用完 `dma_channel_unclaim(ch)`（`app_dma.c:43`）。16 個通道用完後 `dma_claim_unused_channel(true)` 會 panic、`(false)` 會回 -1。
5. **修對齊**：32-bit 傳輸時 src / dst 位址要 4 bytes 對齊；`char` 陣列強轉不一定對齊（`app_dma.c:13`）。不確定就用 `DMA_SIZE_8`，或宣告成 `uint32_t` 陣列。
6. 直接用模板：`dma_copy32(dst, src, n)`（`app_dma.c:46`，n 是 u32 個數）。它已經處理 count = 0、count ≥ 2^28、沒通道（回 -1）、unclaim。

### 怎麼驗證

- 官方練習 `make run` 實際輸出：`1. copy 4096 words  dst matches src`、`2. fill 4096 words  every word is 0xA5A5A5A5`。
- Pico：`app_dma` 開機印 `copy 4096 words: loop=…us memcpy=…us dma=…us  正確=OK`（`app_dma.c:109-110`）和 `overlap: … 正確=OK`（`:137-138`）。沒有實測。
- 搬完一定 `memcmp(dst, src, ...)`，並檢查 `dst` **後面**沒有被寫到（官方 `--mistake` 就是這樣抓到的）。

### 先交一版的最小做法 vs 之後的優化

| 階段 | 做法 |
|---|---|
| 第一版 | 修 count / 遞增 / unclaim，用 blocking 等完成 |
| 優化 1 | 啟動後不等，CPU 去做別的事，要用 `dst` 前才 `wait`（`app_dma.c:128-136`，第 4 段） |

### 常見陷阱

- `dma_fill32` 的來源值要在 DMA 跑完前都存在 → 用 `static`（`app_dma.c:48`）。

## 1.18 情境 2-3-E：通道不夠用（第五個請求）→ 排隊或重用通道（★★）

### 題目可能長這樣（假想範例）

> 傳輸引擎只有 4 個通道，現在同時來了 5 份資料要搬，第 5 份 `claim` 回傳 -1，程式直接當掉。請讓 5 份都正確搬完。

### 判斷依據

- 「通道有限」「claim 失敗」「-1」「第五個」「排隊」「重用」。`engine.h:17` `ENGINE_CHANNELS 4`；`engine.h:31` `engine_claim()` 「沒有空的回 -1」。

### 要打開的檔案、先讀哪幾行

| 檔案 | 先讀 |
|---|---|
| `考試相關資訊/section2-3/transfer-engine/engine.h` | `:17`、`:31-47` |
| `考試相關資訊/section2-3/transfer-engine/engine.c` | `:36` `engine_claim()`、`:95-97` `engine_release()`（還在跑時 release 會停下來報錯） |
| `預製程式碼/pico/app_dma.c` | `:35-36`（`dma_claim_unused_channel(false)`，沒通道回 -1；`TODO(改這裡) 沒通道就改用 CPU 做`） |

### 步驟（實例，用官方 engine 實際跑過）

我寫了 `$S/ch01/five.c`，用官方 `engine.c` 模擬 5 份工作：先 claim 5 次，第 5 次失敗；失敗的那份**等第一個通道做完、release 後再 claim**（重用），然後全部 `memcmp` 檢查。核心片段：

```c
for (int j = 0; j < JOBS; j++) {
    if (ch[j] < 0) { engine_wait(ch[0]); engine_release(ch[0]); ch[j] = engine_claim(); }
    engine_job_t job = { .src = src[j], .dst = dst[j], .count = N, .size = XFER_32,
                         .src_increment = true, .dst_increment = true };
    engine_configure(ch[j], &job);
    engine_start(ch[j]);
}
```

實際執行輸出（host gcc 13.3）：

```text
job 0 claim -> 0
job 1 claim -> 1
job 2 claim -> 2
job 3 claim -> 3
job 4 claim -> -1
job 4 重試 claim -> 0
5 份都搬完：OK
```

Pico 上的對應做法（擇一）：

| 做法 | 程式 |
|---|---|
| 沒通道就用 CPU 做 | `app_dma.c:36` 的 `return -1` 改成 `memcpy(to, from, count * 4); return 0;`（32-bit 時） |
| 等別人做完再用 | `dma_channel_wait_for_finish_blocking(ch_old)` → `dma_channel_unclaim(ch_old)` → 再 `dma_claim_unused_channel(false)` |
| 不要每次 claim | 開機時 claim 固定幾個通道，之後一直重用（不 unclaim） |

### 怎麼驗證

- 每一份都 `memcmp`；故意送「通道數 + 1」份工作測一次。
- Pico 上 RP2350 有 16 個通道，題目的假引擎可能只有 4 個（`app_dma.c:9`）→ 以題目給的數字為準。

### 先交一版的最小做法 vs 之後的優化

- 第一版：失敗就等前一份做完再重用（或退回 CPU 做），保證正確。
- 優化：固定通道池 + 輪流用；或用 chaining 串起來（`prompt工具包/cards/pico-dma.md`【參考卡｜RP2350 DMA 5/8｜chaining、ping-pong、ring】）。

### 常見陷阱

- 通道還在跑就 release，官方 engine 會報 `release while the channel is still running`（`engine.c:97`）；pico-sdk 不會報錯，但可能被別人 claim 走後設定被蓋掉 → 先 `wait` 再 `unclaim`（`app_dma_pio.c:76` 也這樣做）。
- `dma_claim_unused_channel(true)` 沒通道時會 panic（停住），考試時用 `false` 自己處理（`app_dma.c:35`）。

## 1.19 情境 2-3-F：PIO + DMA 串起來（DMA 依 DREQ 從 PIO FIFO 搬資料）（★）

### 題目可能長這樣（假想範例）

> 把 4096 個 u32 送進 PIO（echo 或題目給的 `.pio`），處理完的結果收回記憶體，CPU 不要自己 put / get。

### 判斷依據

- 「DREQ」「DMA 搬到 PIO」「TX FIFO / RX FIFO」「CPU 空出來」。

### 要打開的檔案、先讀哪幾行

`預製程式碼/pico/app_dma_pio.c`（95 行）：`:1-20`（DREQ 是什麼、兩個通道、正確性重點）、`:44-49`（載入 PIO）、`:52-54`（要兩個通道）、`:56-62`（TX 通道：讀遞增、寫不動、DREQ = TX）、`:64-69`（RX 通道：讀不動、寫遞增、DREQ = RX）、`:73`（用 mask 同時啟動）、`:75-77`（等完成）、`:89-93`（收拾）。

### 步驟

1. PIO 先 `pio_add_program` + `pio_claim_unused_sm` + `xxx_program_init`（`app_dma_pio.c:44-49`）。
2. 兩個通道都設 DREQ：`channel_config_set_dreq(&ctx, pio_get_dreq(pio, sm, true))`（`:60`）、`channel_config_set_dreq(&crx, pio_get_dreq(pio, sm, false))`（`:68`）。**DREQ 編號用 `pio_get_dreq()` 算，不要自己寫數字**（`:14`）。
3. 寫 `&pio->txf[sm]`、讀 `&pio->rxf[sm]`（`:62`、`:69`），configure 最後一個參數給 `false`（先不開始）。
4. `dma_start_channel_mask((1u << ch_tx) | (1u << ch_rx));`（`:73`）兩個一起開。
5. 先等 RX（資料全部回來）、再等 TX（`:75-76`），然後 unclaim、停 SM、移除程式（`:89-93`）。
6. 題目的 `.pio` 不是 echo 時：資料寬度要和 `.pio` 的 autopull / autopush 門檻一致（`:19-20`）。

編譯：本章 1.1 的模板 build 已包含 `app_dma_pio`，0 warning。板子上沒有實測。

### 怎麼驗證

- 板子上 `app_dma_pio` 印 `DMA+PIO 4096 words: … us, 結果 OK` 和 CPU put/get 對照組的時間與倍數（`app_dma_pio.c:79-87`）。沒有實測。
- 改過 `echo.pio`（例如 1.11 的反相）後，這裡的 `memcmp` 會 FAIL，要改成和新的預期值比。

### 先交一版的最小做法 vs 之後的優化

- 第一版：CPU 自己 `pio_sm_put_blocking` / `pio_sm_get_blocking`（`app_dma_pio.c:84`），保證正確。
- 優化：DMA + DREQ；CPU 在 `:74` 的 `TODO(改這裡)` 去做別的事。

### 常見陷阱

- 只開 TX 不開 RX → RX FIFO 滿 → SM 卡在 push → TX 卡住，`ch_tx` 永遠 BUSY（`app_dma_pio.c:16-17`）。
- echo 同時用 TX 和 RX，**不能** `fifo_join`（`:18`）。
- DMA_SIZE 改成 8-bit 時，`.pio` 的門檻也要改；窄寫入的 byte lane 行為不確定就維持 32-bit（`:19-20`）。
- `pio_add_program` 失敗回負數，不能直接轉 `uint`（`:45-46`）。
