# 05 提交前檢查

> 用途：每次送 Online Judge 前逐項打勾。給自己看，不需要貼給模型（最後的 `/檢查` 提示除外）。
> 考場規則重點：**不得同時提交多次作答**；不得以任何方式干擾評分系統。
> 最後更新：2026-11

---

## 1. 提交規則（考場規則）

- 一次只能有一份作答在評分中。送出後，**等結果出來再送下一次**。
- 如果提交是透過 `git push` 觸發 GitLab pipeline：push 之後去 GitLab 網頁看 pipeline 狀態，跑完才能再 push。
- 不要嘗試讓評分系統做出不正確的評分（例如偵測測資內容硬寫答案、大量提交）——規則明訂分數不採計並追究責任。
- 題目若有另外規定提交方式或次數，以題目為準。

---

## 2. 提交前檢查清單

### 2.1 正確性

- [ ] 用範例輸入跑過，`diff` 對照預期輸出完全一致。
- [ ] 測過邊界情況：空 / 最小 / 最大輸入、長度不是 4 的倍數、奇數個元素。
- [ ] 多執行緒 / 多核心程式：連續跑 20 次以上，結果都一樣。
- [ ] 沒有編譯警告（至少看過 `-Wall -Wextra` 的警告，確認無害）。

### 2.2 介面與格式

- [ ] 沒有修改題目規定不能改的檔案：`git diff --stat <起始commit>` 檢查改了哪些檔案。
- [ ] 函式簽名、檔名、輸出格式與題目要求一致。
- [ ] **debug 輸出已關閉或移除**，沒有混入 stdout：`grep -rn "printf\|DBG\|puts\|print(" src/`。
- [ ] 沒有留下寫死的測試路徑、測試用的參數。

### 2.3 建置

- [ ] 從乾淨狀態重新編譯成功（`make clean && make`，或刪掉 `build/` 重新 cmake）。
- [ ] 新增的原始檔有加入 CMakeLists.txt / Makefile。
- [ ] 新用到的函式庫有加入 `target_link_libraries`。
- [ ] 編譯設定與評分環境一致（Release / 最佳化等級 / 目標平台 ARM 或 RISC-V）。

### 2.4 版本控制

- [ ] `git status` 乾淨，所有要交的檔案都已 commit。
- [ ] 沒有把建置產物（`build/`、執行檔）意外加入（除非題目要求）。
- [ ] commit 訊息寫清楚這版改了什麼，方便之後回頭找。
- [ ] push 到題目指定的 branch。

### 2.5 送出後

- [ ] 等評分結果，記錄到下方的提交紀錄表。
- [ ] 若分數變低：比較與上一版的差異，必要時回復到最佳版本再提交。

**永遠知道「目前最高分是哪個 commit」**。考試結束前最後確認評分系統採計的是最佳版本（看題目規定：採計最後一次還是最高分一次）。

## 4. 常用 git 指令

```bash
git status
git diff --stat                     # 這次改了哪些檔案
git add <files> && git commit -m "訊息"
git push                            # 或 git push origin <branch>
git log --oneline -10
git tag best-v1                     # 標記目前最好的版本，方便回去
git checkout best-v1 -- src/file.c  # 從標記的版本拿回某個檔案
```

## 5. 給模型的提交前審查

```
/檢查
我準備提交。以下是與上一個版本的 diff：
{{貼 git diff}}

題目限制：{{不能改的檔案 / 介面 / 輸出格式}}

請檢查：
1. 有沒有明顯的 bug（越界、差一、型別、未初始化、資料競爭）
2. 有沒有改到不該改的介面或輸出格式
3. 有沒有殘留的 debug 輸出
4. 邊界情況是否處理（空輸入、非 4 的倍數長度、最大輸入）
5. 新用到的 API 是否需要在 CMake / Makefile 加連結
只列出問題，沒問題的項目回答「OK」即可。
```
